### 레거시 코드 개선을 통한 비즈니스 로직 성능 향상

#### 문제 / 요구사항
- 기존 레거시 코드에서는 비즈니스 로직을 처리하는 쓰레드 내에서
  로그 메시지를 파일에 기록하는 작업까지 함께 수행하고 있었음
- 파일 I/O는 상대적으로 매우 느린 작업이기 때문에,
  비즈니스 로직의 처리 지연 및 전체 성능 저하로 이어짐
- 단순 코드 최적화가 아닌 **구조적인 성능 개선**이 요구됨

#### 접근 방식
- “느린 작업을 빠른 경로에서 제거한다”는 원칙을 기반으로
  비즈니스 로직과 로깅 작업의 실행 경로를 분리
- 로깅을 전담하는 **비동기 Logger 클래스**를 새롭게 설계하여 도입

#### 해결 과정에서 고려한 사항
- **불필요한 문자열 복사 제거**
  - `std::string` 지역 변수가 다른 함수로 전달되는 역할만 하는 경우
    rvalue reference를 사용하여 복사 비용 제거
- **컨테이너 삽입 시 임시 객체 생성 방지**
  - 큐에 로그 메시지를 저장할 때 `push_back` 대신 `emplace_back` 사용
- **메시지 포맷팅 비용 감소**
  - 반복 생성 비용이 큰 `boost::format` 객체를 static으로 관리

#### 부딪힌 문제와 극복
- 단순히 비동기 처리만으로 충분한 성능 개선이 가능한지에 대한 의문
- 로깅 경로 전체를 분석하여
  객체 생성, 복사, 포맷팅 비용까지 포함한 최적화로 접근

#### 결과 및 배운 점
- 비즈니스 로직 경로에서 파일 I/O 제거로 성능 및 안정성 개선
- 성능 최적화는 “빠른 코드 작성”이 아니라
  **느린 작업을 어디에서 제거하느냐의 문제**라는 점을 체득

### Hyperscan 기반 정규표현식 패턴 매칭 라이브러리 제작

#### 문제 / 요구사항
- 대규모 정규표현식 패턴을 고속으로 매칭해야 하는 환경
- 단순 라이브러리 사용이 아닌 다음 요구사항 충족 필요
  - Thread-Safe 보장
  - Pattern DB compile 비용 최소화
  - Compile 불가능한 패턴에 대한 사전 필터링

#### 접근 방식
- Hyperscan을 직접 노출하지 않고
  도메인 환경에 맞는 **추상화된 라이브러리 형태로 설계**
- Pattern DB와 실행 환경을 분리하여 재사용성 확보

#### 성능 개선을 위한 단계적 접근
1. **mutex 기반 보호**
   - 구현은 단순하지만 Lock 경합으로 성능 저하 발생
2. **scratch space를 매 호출마다 할당**
   - Lock 경합 감소, 대신 alloc/free 비용 증가
3. **thread별 scratch space clone 관리**
   - Lock 구간 최소화 및 성능 안정화

#### 부딪힌 문제와 극복
- 성능과 안정성 사이의 트레이드오프
- 단계별 개선을 통해 실제 성능 특성을 비교하고 최적의 구조 선택

#### 결과 및 배운 점
- 고성능 시스템에서 Lock 설계는 구현 문제가 아니라
  **아키텍처 설계의 문제**임을 체득
- Thread-local 리소스 관리의 중요성 이해

## Shared Memory 기반 IPC 설계 및 운영 안정성 개선

### 문제 / 요구사항
- 프로세스 간 대용량 데이터를 **낮은 지연(latency)**으로 공유할 필요가 있음
- 직렬화 및 데이터 복사 비용을 최소화해야 하는 환경
- 공유메모리 기반 구조 특성상 **데이터 생성 시점과 로드 타이밍 불일치**로 인한 안정성 문제가 발생할 수 있음

### 접근 방식
- `boost::interprocess`를 활용한 공유메모리 IPC 구조 설계
- 외부 데이터 소스(DB/파일)를 로드하여 **객체 자체를 공유메모리에 적재**하는 방식 채택
- 다수의 프로세스가 동일한 공유메모리를 참조하는 구조

### 기본 구현 및 기술적 고려
- `managed_shared_memory`
  - 공유메모리 세그먼트 생성 및 수명 관리
- `offset_ptr`
  - 프로세스 주소 공간과 무관한 위치 독립적 포인터 접근
- 공유메모리 상에서 STL container 사용

### 운영 환경에서 발생한 문제 상황
- 외부 데이터 소스가 **배포/갱신되는 과정 중** 공유메모리 로더 프로세스가 **완전히 준비되지 않은 데이터**를 반복적으로 로드 시도
- 이로 인해:
  - 데이터 파싱/로딩 실패가 발생했음에도
  - 시스템은 로드가 완료된 것으로 잘못 인식하는 상태 발생
- 이후 데이터가 정상 상태가 되었음에도 **공유메모리 재로딩이 수행되지 않는 장애 상황**으로 이어짐

#### 문제의 본질
- 로드 성공 여부 판단이
  - 실제 데이터 무결성 검증이 아닌
  - 단순 완료 플래그 기반으로 이루어지고 있었음
- 즉, **부분적으로 실패한 로드가 성공으로 기록되는 구조적 결함**이 존재

### 개선 설계 및 조치

#### 1. 실패 내성(Failure Tolerance) 강화
- 외부 데이터 로드에 실패한 경우:
  - 기존에 구축된 공유메모리를 그대로 유지
  - 불완전한 데이터로 공유메모리를 덮어쓰지 않도록 방어
- 시스템이 항상 **최소한의 유효 상태**를 유지하도록 설계

#### 2. 메타데이터 기반 상태 관리 도입
- 공유메모리 로드 완료 여부를 단일 플래그로 판단하지 않도록 개선
- 별도의 메타데이터 파일을 도입하여 다음 정보를 관리:
  - 로더(Producer) 버전 정보
  - 데이터 소스의 배포 시점
  - 향후 확장을 고려한 reserved 영역

#### 3. Consumer 측 검증 로직 강화
- 공유메모리를 사용하는 프로세스(Consumer)가 메타데이터를 기반으로 **자신이 신뢰할 수 있는 상태인지 검증**
- 로더 버전 불일치 또는 신뢰 불가 상태인 경우:
  - 오류 로그 기록
  - 공유메모리를 우회하여 데이터 소스를 직접 로드하는 **Fallback 경로**로 전환

### 결과 및 배운 점
- 공유메모리 IPC의 안정성은 단순한 동기화 문제가 아니라 **데이터 생성·배포·로드 전 과정의 상태 관리 문제**임을 확인
- IPC 설계에서는 성능뿐 아니라 **신뢰 모델과 실패 시나리오를 명확히 정의하는 것이 핵심**이라는 점을 학습

### 추가 사례: 공유메모리 접근 중 `fork()` 호출로 인한 시스템 지연 현상 분석

#### 문제 상황
- 공유메모리에 접근하는 쓰레드가 존재하는 상태에서, 동일 프로세스 내에서 주기적으로 새로운 프로세스를 생성(`fork`)하는 구조에서 시스템 전체가 **잠시 멈춘 것처럼 보이는 현상**이 관찰됨
- 이 시점에 네트워크 레벨에서도 `ping` 지연과 같은 **전반적인 시스템 응답성 저하**가 함께 발생

#### 원인 분석 (구조적 관점)

이 문제는 단일 원인이 아닌 **프로세스 생성 방식, 메모리 관리, 멀티스레드 실행 모델**이 맞물리며 발생한 구조적 부작용으로 판단됨.

1. **프로세스 생성 시 메모리 스냅샷 비용**
   - 프로세스 생성 시, 운영체제는 부모 프로세스의 메모리 상태를 자식 프로세스가 참조할 수 있도록 내부 메모리 구조를 정합성 있게 복제
   - 이 과정에서 메모리 관리 관련 전역 리소스에 대한 커널 레벨 동기화가 발생하며, 짧지만 전체 실행 흐름에 영향을 줄 수 있음

2. **공유메모리 사용과의 충돌**
   - 공유메모리는 여러 실행 흐름이 동시에 접근하는 영역이므로 프로세스 생성 시점에는 해당 메모리 영역의 상태를 안전하게 보장하기 위한 추가적인 동기화가 필요
   - 공유메모리에 대한 빈번한 접근이 있는 상태에서 프로세스 생성이 발생하면 해당 접근 경로가 일시적으로 지연될 수 있음

3. **멀티스레드 환경에서의 프로세스 생성**
   - 멀티스레드 프로세스에서 프로세스 생성이 수행될 경우, 호출 쓰레드를 제외한 다른 쓰레드들은 일시적으로 실행이 중단됨
   - 쓰레드 수가 많거나 공유 자원 접근이 활발한 상태에서는 이 짧은 정지 구간이 시스템 전반의 지연으로 체감될 수 있음

#### 문제의 본질
- 해당 현상은 특정 API의 버그가 아니라 **고빈도 공유메모리 접근 + 멀티스레드 환경 + 프로세스 생성**이 결합되었을 때 나타나는 **운영체제 수준의 설계 특성**에 기인한 문제였음
- 즉, 애플리케이션 로직의 문제가 아니라 **시스템 호출 선택과 실행 위치에 대한 설계 문제**로 판단

#### 개선 방향 및 설계 교훈
- 프로세스 생성(`fork`)을 메인 프로세스의 실행 경로에서 제거
- 메인 프로세스는 별도의 데몬 프로세스와 **Unix Domain Socket 기반 IPC 통신만 수행하는 구조로 재설계**
- 실제 프로세스 생성 및 외부 명령 실행은 전용 데몬 프로세스에서만 수행하도록 역할 분리

이 구조를 통해:
- 멀티스레드 + 공유메모리 접근 중 `fork()` 호출로 인해 발생하던 메모리 스냅샷 및 전역 동기화 비용을 **완전히 회피**
- 메인 프로세스의 메모리 공간이 복제 대상이 되지 않도록 하여 시스템 전반의 일시 정지(stall) 현상 제거
- 프로세스 생성 비용을 공유메모리 기반 데이터 경로와 **물리적으로 분리**

#### 설계 관점에서의 교훈
- `fork()`는 단순한 시스템 호출이 아니라 **프로세스 전체 메모리 모델에 영향을 주는 고비용 연산**
- 고성능·공유메모리 기반 시스템에서는 프로세스 생성 위치 자체가 아키텍처 설계 요소가 됨
- 성능 문제를 해결하기 위해 호출 빈도를 줄이는 수준이 아니라 **아키텍처 레벨에서 책임을 분리하는 것이 근본 해결책**
